Resumo
Este trabalho apresenta o desenvolvimento e a validação de um relógio inteligente baseado em ESP32, concebido como um sistema ciberfísico com integração entre hardware, firmware e interface web embarcada. O objetivo principal foi implementar uma solução funcional capaz de exibir hora local em display LCD 16x2, exibir imagem relacionada ao clima em um display OLED juntamente com um menu, gerenciar alarmes configuráveis com sinalização sonora, coletar dados ambientais por sensor DHT22, sincronizar horário por RTC DS3231/NTP, e disponibilizar monitoramento de desempenho em tempo real por navegador. A metodologia adotada foi incremental e modular, com etapas de configuração de periféricos, implementação de serviços de comunicação, construção da máquina de estados local no display, exposição de APIs HTTP e consolidação de mecanismos de persistência em SPIFFS. Também foram aplicadas técnicas de observabilidade, incluindo logs com níveis de severidade, histórico de métricas e rotinas de backup/restauração de dados. Entre os principais resultados, o sistema alcançou operação estável com interface web para ajuste de hora, alarmes, parâmetros de coleta e troca de rede Wi-Fi sem necessidade de regravação do firmware. O projeto apresentou ainda monitoramento de tempos de execução (loop, leitura de RTC, leitura de botões, atualização de display e requisições de clima), além de indicadores de heap, stack, uso de flash e quantidade de tasks do sistema. Como conclusão, a solução atendeu aos requisitos funcionais centrais de integração ciberfísica, configurabilidade remota e observabilidade, demonstrando aplicabilidade prática dos conceitos da disciplina. 1 Introdução
Com a popularização da Internet das Coisas (IoT), sistemas embarcados passaram a desempenhar papel central em soluções ciberfísicas capazes de integrar sensores, atuadores, comunicação em rede e interfaces de monitoramento. Nesse contexto, o uso do ESP32 se destaca por combinar conectividade Wi-Fi, capacidade de processamento e ecossistema de desenvolvimento consolidado. Este projeto foi motivado pela necessidade de construir um sistema real e funcional que ultrapasse a lógica de um relógio digital simples, incorporando um sistema de previsão do tempo por API de terceiros, incluindo também aí projeto geral observabilidade, persistência e configuração remota.
O problema abordado consiste em projetar um dispositivo compacto que, além de exibir hora e alarmes, mostre também informações sobre o tempo, preparando a pessoa para o dia, e que também opere como plataforma de monitoramento de performance do próprio firmware, com dados acessíveis em interface web embarcada. A relevância acadêmica do tema está em aplicar conceitos de sistemas ciberfísicos, desempenho, gerenciamento de memória e comunicação entre camadas (hardware, firmware e software de interface).
Como solução, foi desenvolvido um relógio inteligente com RTC DS3231, display LCD, display OLED, sensor DHT22 e saída de áudio I2S via MAX98357A. O firmware implementa máquina de estados para interação local por botões, servidor HTTP para configuração e monitoramento remoto, e armazenamento de configurações/históricos em SPIFFS. Este documento está organizado em objetivos, requisitos, fundamentação teórica, metodologia, desenvolvimento, testes, resultados e conclusões.

(f) Persistir configurações e históricos na flash com rotinas de backup e restauração.

4 Fundamentação Teórica
4.1 Sistemas Ciberfísicos
Sistemas ciberfísicos integram processos computacionais e componentes físicos em malhas de monitoramento e controle. Neste projeto, sensores (DHT22/RTC), atuadores (OLED/LCD/áudio), conectividade (Wi-Fi) e software embarcado compõem uma arquitetura CPS orientada a observabilidade local e remota.
4.2 Concorrência e Paralelismo em Sistemas Embarcados 
Este projeto explora o dual-core através do FreeRTOS: TaskAquisicao executa em Core 0 (responsável por I2C/WiFi/HTTP) coletando dados de sensores continuamente, enquanto TaskUI em Core 1 gerencia display e servidor HTTP. TaskAudio e TaskPersistencia podem executar em qualquer núcleo, priorizadas por nivel de importância. Comunicação inter-core ocorre por fila FIFO (sensorQueue) com xQueueOverwrite, evitando bloqueios e mantendo latência de eventos baixa.
4.3 Gerenciamento de Memória e Desempenho 
Este projeto minimiza uso de RAM alocando código em PROGMEM: melodias (5 × ~200 bytes), HTML/CSS/JavaScript (>5 KB), e arrays de lookup. Ring buffer de logs usa 4 KB fixo em RAM. Histórico de performance (PERF_HIST_SIZE=288, 7 métricas) utiliza ~8 KB em RAM estático. Monitoramento contínuo de heap mínimo, stack high water mark e PSRAM via esp_get_free_heap_size() permite detectar vazamentos e regressões. Princípio adotado: minimizar a alocação dinâmica, usar alocadores de pilha para objetos temporários.

4.4 Sistemas Operacionais Embarcados e Uso de RTOS
O ESP32 executa FreeRTOS como base. Este projeto utiliza 4 tasks FreeRTOS com xTaskCreatePinnedToCore para controle de afinidade de núcleo, prioridades definidas por configMAX_PRIORITIES (25 no ESP32), e filas para sincronização. TaskAquisicao (prioridade 23) lê sensores periodicamente (5s DHT, 10min clima). TaskUI (prioridade 22) renderiza displays e processa requ. HTTP. TaskAudio (prioridade 21) toca as notas. TaskPersistencia (prioridade 17) gerencia backup em SPIFFS. Métricas de runtime como heap, stack watermark e state das tasks são coletadas via uxTaskGetStackHighWaterMark()
4.5 Gerenciamento de Energia em Dispositivos IoT ////////////// melhorar
Técnicas como modem sleep, light sleep e deep sleep são relevantes para autonomia energética. No estado atual, o firmware prioriza disponibilidade e latência de interface, sem aplicar modos agressivos de economia, caracterizando oportunidade clara de evolução.
4.6 Monitoramento, Logging e Observabilidade em Sistemas Computacionais
Observabilidade envolve expor logs, métricas e eventos para compreender comportamento interno. Este projeto implementa:
Buffer circular de logs (4 KB, logBuffer[LOG_BUF_SIZE]) com níveis [INFO]/[WARN]/[ERROR], gravável em /log_backup.txt via SPIFFS;
Sete métricas de performance (loop time, clima API, RTC, botões, DHT temp, display, DHT umidade) em array PERF_HIST[7][288];
Histórico em arquivo binário /perf_backup.bin com CRC para validação;
Interface web expondo JSON (endpoints /api/log, /api/perf, /api/flash) com gráficos HTML5 canvas. 
Amostragem de performance: 1 ponto a cada 5 segundos, permitindo 24 minutos de histórico sem deslizar.
5 Metodologia
5.1 Padrões de Arquitetura de Firmware
Este projeto adota padrões produtores-consumidores: TaskAquisicao (produtor) coleta dados e enfileira em sensorQueue; TaskUI (consumidor) lê periodicamente (500ms) via xQueueReceive com timeout 0ms (não-bloqueante). Botões disparam GPIO interrupts que enfileiram eventos em buttonEventQueue. TaskAudio consome fila de alarmes. TaskPersistencia valida e grava estado. Todos os dados compartilhados são mutex-protegidos ou enfileirados, evitando race conditions. Arquivos de configuração (WiFi, horario, alarmes) são mapeados em estruturas compatíveis com SPIFFS, permitindo serialização/desserialização.
5.2 Ciclo de Boot e Inicialização
Máquina de estados sequencial:
BOOT_INIT: configura GPIO/I2C, inicializa libs;
BOOT_RTC: sincroniza hora via NTP/RTC;
BOOT_DHT: testa sensor DHT22;
BOOT_CLIMA: valida conectividade WiFi; 
(5-9) ativa tasks FreeRTOS (Aquisicao, UI, Audio, Persistencia), carrega config de SPIFFS, exibe splash screen.
Cada etapa aguarda intervalo para detectar hang-ups. Logs de boot com timestamps permitem auditoria de sequência.
5.3 Integração Progressiva de Sensores e Atuadores // falar melhor
A integração ocorreu de forma incremental: display e RTC, depois Wi-Fi/API, em seguida DHT22, alarmes sonoros I2S e por fim persistência e dashboard web.
5.4 Desenvolvimento da Interface Web
A interface foi embarcada no próprio firmware por string HTML com CSS e JavaScript nativos, sem dependências externas. A comunicação ocorre por endpoints REST simples (GET/POST) retornando texto e JSON.

6.3 Estrutura das Tasks
A TaskAquisicao é executada no Core 0, possui prioridade alta (23), intervalo de execução de 5 segundos e utiliza 4096 bytes de stack. Sua principal responsabilidade é coletar os dados ambientais do sistema através do sensor DHT22, realizando leituras periódicas de temperatura e umidade. Além disso, a cada 10 minutos, a tarefa realiza uma requisição HTTP para a API Meteosource, obtendo informações climáticas atualizadas. Para evitar bloqueios excessivos da aplicação, as requisições possuem timeout de 10 segundos. Os dados coletados são encapsulados em uma estrutura SensorData e enviados para a fila sensorQueue utilizando a função xQueueOverwrite(), garantindo que apenas a informação mais recente permaneça disponível mesmo quando a fila estiver cheia. Em caso de falhas na leitura dos sensores ou na comunicação com a API, logs são registrados.


A TaskUI é executada no Core 1, possui prioridade média (22), intervalo de execução de 500 milissegundos e utiliza 4096 bytes de stack. Essa tarefa é responsável pela interação com o usuário, consumindo os dados armazenados na sensorQueue através da função xQueueReceive() configurada com timeout de 0 ms, evitando bloqueios durante a execução. As informações recebidas são enviadas tbm para um display OLED SSD1306 (endereço I2C 0x3C), apresentando dados de clima em formato de ícones, e menus relacionados aos alarmes configurados pelo usuário. Paralelamente, um display LCD I2C (endereço 0x27) exibe as informações principais. Além da interface física, a TaskUI também executa um servidor HTTP baseado na biblioteca WebServer, processando requisições das rotas GET /api/, POST /config/ e DELETE /logs, permitindo monitoramento e configuração remota do sistema por meio de uma interface web.
A TaskAudio opera com prioridade média (21), utiliza 2048 bytes de stack e executa verificações a cada 50 milissegundos. Sua função é gerenciar os alarmes sonoros do sistema. A tarefa permanece aguardando eventos em uma fila específica de alarmes e, quando acionada, reproduz melodias através de um módulo MAX98357A conectado à interface I2S do ESP32. As músicas são armazenadas em memória utilizando arrays de notas em PROGMEM, incluindo melodias como Bossa Nova, Beethoven e outras opções configuráveis. A reprodução ocorre de forma não bloqueante, tocando uma nota a cada 50 ms, permitindo que as demais tarefas continuem executando normalmente. A comunicação I2S utiliza as portas GPIO26 (BCLK), GPIO25 (LRC) e GPIO27 (DIN). Após a execução completa da melodia selecionada, a tarefa retorna ao estado de espera por novos eventos.


A TaskPersistencia possui prioridade baixa (17), utiliza 3072 bytes de stack e não apresenta afinidade fixa com nenhum núcleo, permitindo que o escalonador escolha dinamicamente o melhor processador disponível. Diferentemente das demais tarefas, sua execução é baseada em temporizadores periódicos. Um callback é acionado a cada 30 minutos para realizar o backup dos logs do sistema, a cada 2 horas para armazenar métricas de desempenho e a cada 6 horas para executar verificações de integridade dos dados. Essas operações invocam respectivamente as funções salvarLogFlash(), salvarPerfFlash() e validarIntegridadeFlash(). Os dados são gravados no sistema de arquivos SPIFFS, utilizando arquivos como /log_backup.txt e /perf_backup.bin. Para garantir confiabilidade e detectar possíveis corrupções de dados, todos os registros armazenados passam por validação utilizando o algoritmo CRC-32.


6.4 Interrupções de Hardware
Fluxo de Botão (GPIO4/GPIO18):
1. Pino no estado HIGH (PULLUP ativo).
2. Usuário pressiona: pino vai para LOW.
3. GPIO Interrupt em borda FALLING dispara (attachInterrupt com modo FALLING).
4. ISR (IRAM_ATTR btn1_isr / btn2_isr) executa em < 1µs:
   - Valida se debounce não está pendência (flag btn1_pending/btn2_pending).
   - Seta flag como pending.
   - Inicia timer via esp_timer_start_once(debounce_timer, 20000µs).
5. Após 20ms, callback de debounce (btn1_debounce_callback / btn2_debounce_callback) executa:
   - Lê pino novamente (confirma que ainda está LOW).
   - Se confirmado: cria ButtonEvent e enfileira via xQueueSendFromISR(buttonEventQueue, &event, NULL).
   - Limpa flag pending.
6. Loop principal (MainLoop.cpp) consome buttonEventQueue periodicamente, processando evento (mudar alarme, ativar relogio, etc).


Benefícios:
- Debounce por timer evita bounces mecânicos (~20-50ms).
- ISR rápida não bloqueia outras tasks.
- Fila de eventos desacopla detecção (ISR) de processamento (main loop).
- Latência de clique ~ 21-30ms (ISR + timer + fila read interval máx 500ms se em TaskUI).


6.5 Estratégias de Gerenciamento de Energia
A estratégia de economia de energia implementada baseia-se em ciclos controlados de Light Sleep. O firmware orquestra a entrada nesse estado configurando fontes híbridas de despertar: um temporizador interno (timer wake-up) para atualizações periódicas e interrupções físicas via GPIO (ext0 wake-up) nos botões de controle. A integridade operacional é monitorada através de um sistema de observabilidade que registra logs detalhados no momento da suspensão (indicando a duração prevista) e imediatamente após o despertar (sinalização de status "Woke"), permitindo a validação da estabilidade térmica e de performance do firmware.
6.6 Estrutura e Organização da Interface Web
A interface contém três abas principais:
- Principal: Relógio digital em tempo real, ajuste de hora, gerenciamento dos 3 alarmes (hora, minuto, melodia, on/off), temperatura local (DHT22), umidade local (DHT22) e previsão de clima da API.
- Monitoramento: 4 sub-abas (Logs, Serial, Flash, Gráficos) com visualização de eventos, ring buffer de logs, backup da flash, download/upload de histórico de performance, e 7 gráficos em tempo real.
- Sobre: Identificação do projeto (v3.1.0), integrantes, link GitHub, campos de configuração (intervalos DHT, clima, backup), e troca de credenciais WiFi.
Endpoints principais:
  GET  /                        → Página HTML + CSS + JavaScript (embarcado em PROGMEM)
  GET  /api/log                 → Log em texto (ring buffer)
  GET  /api/alarmes             → JSON com alarmes, tempos, clima, uptime
  GET  /api/hora                → Ajusta RTC (parâmetros h, m)
  GET  /api/alarme              → Edita alarme (parâmetros id, h, m, mel)
  GET  /api/alarme/toggle       → Liga/desliga alarme (parâmetro id)
  GET  /api/clima               → Força atualização do clima
  GET  /api/serial              → Log serial (mesmo do /api/log)
  GET  /api/flash               → Log salvo em SPIFFS
  GET  /api/config              → Retorna parâmetros (JSON)
  GET  /api/config/set          → Salva parâmetros (query: dht, clima, backup em ms)
  GET  /api/wifi/set            → Troca WiFi e reconecta (query: ssid, pass)
  GET  /api/perf                → Histórico de performance (JSON com 7 séries)
  GET  /api/salvar              → Força backup completo na flash
  GET  /api/download_perf       → Exporta histórico em formato texto (CSV-like)
  POST /api/upload_perf         → Importa histórico de arquivo texto
6.7 Mecanismos de Persistência de Dados
Persistência em SPIFFS (flash):
- /wifi_config.txt: SSID (linha 1) e senha (linha 2) em texto simples.
- /config_params.txt: Três valores em ms (DHT intervalo, Clima intervalo, Backup intervalo) separados por newline.
- /log_backup.txt: Snapshot de estado incluindo timestamp, alarmes (hora, minuto, status), temperatura, heap e uptime.
- /perf_hist.bin: Histórico binário de 7 séries de 60 amostras (uint32_t cada) com estrutura: [array PERF_FUNCOES][PERF_HIST_SIZE], posição atual, flag de full.
Suporte adicional para exportação/importação textual do histórico de performance via download/upload de backup (endpoints /api/download_perf e /api/upload_perf).
Amostragem: 1 ponto a cada 5 segundos (PERF_SAMPLE_MS = 5000). Com 60 amostras, total = 300 segundos = 5 minutos de histórico.
Backup automático: Executado a cada 2 horas (padrão configurável via /api/config/set) ou sob demanda (/api/salvar).

Métricas coletadas (7 séries em histórico circular de 5 minutos):

  [3] tempoLeituraBotoesUs: Tempo de debounce dos botões (ms)
  [4] dhtTemperature: Temperatura medida pelo DHT22 (°C x10, inteiro)
  [5] tempoAtualizarDisplayUs: Tempo de redesenho do OLED (ms)
  [6] dhtHumidity: Umidade medida pelo DHT22 (% x10, inteiro)
Amostragem: 1 ponto a cada 5 segundos, totalizando 300 segundos (5 minutos) de histórico.
Indicadores adicionais: CPU estimada (%), heap livre/mínimo, stack disponível, uso de flash, PSRAM total/livre, número de tasks, status WiFi (CONECTADO/DESCONECTADO), status AP (ATIVO/INATIVO).

9 Conclusão
O projeto Relógio Inteligente ESP32 demonstrou a viabilidade de implementar um sistema ciberfísico completo em plataforma embarcada de baixo custo, com integração entre sensores, atuadores, conectividade e interface web. Os objetivos gerais e específicos foram alcan dados, com destaque para: (1) Multitarefa verdadeira em dual-core com 4 tasks FreeRTOS pinadas e comunicação por fila; (2) Interrupções de hardware com ISR curta e debounce por timer; (3) Persistência com histórico de 288 amostras (24 min) e validação CRC; (4) Configuração remota sem reflash; (5) Observabilidade integrada com 7 métricas em tempo real. Apêndice C - Manual de Usuário
1) Alimentar o ESP32 (5V USB ou bateria).
2) Verificar no OLED o IP local (se WiFi conectado) ou AP de recuperação (se WiFi falhar). LCD 16x2 também exibe hora e IP/AP.
3) Acessar no navegador: http://<ip_local> (ex: http://192.168.0.20) ou http://192.168.4.1 (AP padrão).
4) Na aba "Principal": Ajustar hora do sistema, configurar 3 alarmes (hora, minuto, melodia, on/off), visualizar temperatura local (DHT22), umidade local, e clima da API.
5) Na aba "Monitoramento": Visualizar logs em tempo real (Logs), log serial (Serial), backup da flash (Flash), ou 7 gráficos de performance (Gráficos). Botões para forçar salvamento, baixar/restaurar backup de histórico.
6) Na aba "Sobre": Identificação do projeto (v3.1.0), ajustar intervalos de leitura DHT (ms), intervalo de clima (ms), intervalo de backup (ms), trocar SSID e senha do WiFi.
7) Usar botão 1 (GPIO4) para navegar menus no OLED; botão 2 (GPIO18) para confirmar. No display OLED: Relógio → Menu → Alarmes/Hora → Editar.
8) O sistema salva automaticamente configurações na flash. WiFi será reconectado ao reiniciar.
9) Para resetar: Renomeie /wifi_config.txt em SPIFFS ou faça format via Arduino IDE.
