Resumo
Este trabalho apresenta o desenvolvimento e a validação de um relógio inteligente baseado em ESP32, concebido como um sistema ciberfísico com integração entre hardware, firmware e interface web embarcada. O objetivo principal foi implementar uma solução funcional capaz de exibir hora local em display OLED, gerenciar alarmes configuráveis com sinalização sonora, coletar dados ambientais por sensor DHT22, sincronizar horário por RTC DS3231/NTP, e disponibilizar monitoramento de desempenho em tempo real por navegador. A metodologia adotada foi incremental e modular, com etapas de configuração de periféricos, implementação de serviços de comunicação, construção da máquina de estados local no display, exposição de APIs HTTP e consolidação de mecanismos de persistência em SPIFFS. Também foram aplicadas técnicas de observabilidade, incluindo logs com níveis de severidade, histórico de métricas e rotinas de backup/restauração de dados. Entre os principais resultados, o sistema alcançou operação estável com interface web para ajuste de hora, alarmes, parâmetros de coleta e troca de rede Wi-Fi sem necessidade de regravação do firmware. O projeto apresentou ainda monitoramento de tempos de execução (loop, leitura de RTC, leitura de botões, atualização de display e requisições de clima), além de indicadores de heap, stack, uso de flash e quantidade de tasks do sistema. Como conclusão, a solução atendeu aos requisitos funcionais centrais de integração ciberfísica, configurabilidade remota e observabilidade, demonstrando aplicabilidade prática dos conceitos da disciplina. Abstract
This work presents the development and validation of a smart clock based on ESP32, designed as a cyber-physical system integrating hardware, firmware, and an embedded web interface. The main objective was to implement a functional solution capable of displaying local time on an OLED screen, managing configurable alarms with audio signaling, collecting environmental data through a DHT22 sensor, synchronizing time using DS3231 RTC/NTP, and providing real-time performance monitoring through a web browser. The adopted methodology was incremental and modular, with stages for peripheral setup, communication service implementation, local state-machine design for the display, HTTP API exposure, and SPIFFS-based data persistence mechanisms. Observability techniques were also applied, including severity-based logging, metric history, and backup/restore routines. As main results, the system achieved stable operation with a web interface for time/alarm configuration, sensor collection parameters, and Wi-Fi network update without firmware reflashing. The project also provided execution-time monitoring (main loop, RTC read, button read, display update, and weather API requests), in addition to heap, stack, flash usage and system task indicators. In conclusion, the solution met the core functional requirements of cyber-physical integration, remote configurability, and observability, demonstrating practical applicability of course concepts. 1 Introdução
Com a popularização da Internet das Coisas (IoT), sistemas embarcados passaram a desempenhar papel central em soluções ciberfísicas capazes de integrar sensores, atuadores, comunicação em rede e interfaces de monitoramento. Nesse contexto, o uso do ESP32 se destaca por combinar conectividade Wi-Fi, capacidade de processamento e ecossistema de desenvolvimento consolidado. Este projeto foi motivado pela necessidade de construir um sistema real e funcional que extrapolasse a lógica de um relógio digital simples, incorporando observabilidade, persistência e configuração remota.
O problema abordado consiste em projetar um dispositivo compacto que, além de exibir hora e alarmes, opere como plataforma de monitoramento de performance do próprio firmware, com dados acessíveis em interface web embarcada. A relevância acadêmica do tema está em aplicar conceitos de sistemas ciberfísicos, desempenho, gerenciamento de memória e comunicação entre camadas (hardware, firmware e software de interface).
Como solução, foi desenvolvido um relógio inteligente com RTC DS3231, display OLED, sensor DHT22 e saída de áudio I2S via MAX98357A. O firmware implementa máquina de estados para interação local por botões, servidor HTTP para configuração e monitoramento remoto, e armazenamento de configurações/históricos em SPIFFS. Este documento está organizado em objetivos, requisitos, fundamentação teórica, metodologia, desenvolvimento, testes, resultados e conclusões.
2 Objetivo
2.1 Objetivo Geral
Desenvolver, implementar e validar um sistema ciberfísico embarcado com ESP32, capaz de integrar relógio em tempo real, monitoramento ambiental, alarmes sonoros, interface web de configuração e monitoramento de desempenho com persistência de dados.
2.2 Objetivos Específicos
(a) Integrar RTC DS3231, display OLED SSD1306, sensor DHT22, módulo I2S MAX98357A e botões físicos ao ESP32.
(b) Implementar firmware modular em C++ com boot por estados e loop principal não bloqueante.
(c) Disponibilizar interface web embarcada para ajuste de hora, alarmes, parâmetros operacionais e troca de Wi-Fi.
(d) Implementar sistema de logs com níveis de severidade e visualização remota.
(e) Coletar e exibir métricas de desempenho (tempo de funções, heap, stack, flash, PSRAM e estado de conectividade).
(f) Persistir configurações e históricos na flash com rotinas de backup e restauração.

4 Fundamentação Teórica
4.1 Sistemas Ciberfísicos
Sistemas ciberfísicos integram processos computacionais e componentes físicos em malhas de monitoramento e controle. Neste projeto, sensores (DHT22/RTC), atuadores (OLED/áudio), conectividade (Wi-Fi) e software embarcado compõem uma arquitetura CPS orientada a observabilidade local e remota.
4.2 Concorrência e Paralelismo em Sistemas Embarcados //////////////////////////// melhorar descrição com nosso projeto
Em sistemas embarcados, concorrência ocorre quando múltiplas atividades compartilham tempo de CPU. Mesmo com loop principal único na aplicação, o ambiente ESP32 opera sobre FreeRTOS e pilhas de rede em paralelo, exigindo desenho não bloqueante para manter responsividade da interface e estabilidade temporal.
4.3 Gerenciamento de Memória e Desempenho ////////////////////// melhorar
O uso de PROGMEM para melodias e HTML reduz pressão sobre RAM. A coleta de heap mínimo/atual, stack disponível e tempos de execução por função permite detectar gargalos e regressão de desempenho ao longo da evolução do firmware.
4.4 Sistemas Operacionais Embarcados e Uso de RTOS   /////////// tbm
O ESP32 utiliza FreeRTOS como base do runtime. Embora a aplicação não instancie tasks customizadas, recursos do RTOS são utilizados indiretamente pelo framework (rede, temporização e agendamento), com métricas de runtime expostas na interface.
4.5 Gerenciamento de Energia em Dispositivos IoT ////////////// melhorar
Técnicas como modem sleep, light sleep e deep sleep são relevantes para autonomia energética. No estado atual, o firmware prioriza disponibilidade e latência de interface, sem aplicar modos agressivos de economia, caracterizando oportunidade clara de evolução.
4.6 Monitoramento, Logging e Observabilidade em Sistemas Computacionais /// melhorar especificando o buffer
Observabilidade envolve registrar estados internos por logs, métricas e eventos. O sistema implementa logs em buffer circular, exportação de dados, histórico de performance e APIs para consulta remota, permitindo análise operacional sem acesso físico ao microcontrolador.

6.6 Estrutura e Organização da Interface Web
A interface contém três abas principais:
- Principal: Relógio digital em tempo real, ajuste de hora, gerenciamento dos 3 alarmes (hora, minuto, melodia, on/off), temperatura local (DHT22), umidade local (DHT22) e previsão de clima da API.
- Monitoramento: 4 sub-abas (Logs, Serial, Flash, Gráficos) com visualização de eventos, ring buffer de logs, backup da flash, download/upload de histórico de performance, e 7 gráficos em tempo real.
- Sobre: Identificação do projeto (v3.1.0), integrantes, link GitHub, campos de configuração (intervalos DHT, clima, backup), e troca de credenciais WiFi.
Endpoints principais:
  GET  /                        → Página HTML + CSS + JavaScript (embarcado em PROGMEM)
  GET  /api/log                 → Log em texto (ring buffer)
  GET  /api/alarmes             → JSON com alarmes, tempos, clima, uptime
  GET  /api/hora                → Ajusta RTC (parâmetros h, m)
  GET  /api/alarme              → Edita alarme (parâmetros id, h, m, mel)
  GET  /api/alarme/toggle       → Liga/desliga alarme (parâmetro id)
  GET  /api/clima               → Força atualização do clima
  GET  /api/serial              → Log serial (mesmo do /api/log)
  GET  /api/flash               → Log salvo em SPIFFS
  GET  /api/config              → Retorna parâmetros (JSON)
  GET  /api/config/set          → Salva parâmetros (query: dht, clima, backup em ms)
  GET  /api/wifi/set            → Troca WiFi e reconecta (query: ssid, pass)
  GET  /api/perf                → Histórico de performance (JSON com 7 séries)
  GET  /api/salvar              → Força backup completo na flash
  GET  /api/download_perf       → Exporta histórico em formato texto (CSV-like)
  POST /api/upload_perf         → Importa histórico de arquivo texto
6.7 Mecanismos de Persistência de Dados
Persistência em SPIFFS (flash):
- /wifi_config.txt: SSID (linha 1) e senha (linha 2) em texto simples.
- /config_params.txt: Três valores em ms (DHT intervalo, Clima intervalo, Backup intervalo) separados por newline.
- /log_backup.txt: Snapshot de estado incluindo timestamp, alarmes (hora, minuto, status), temperatura, heap e uptime.
- /perf_hist.bin: Histórico binário de 7 séries de 60 amostras (uint32_t cada) com estrutura: [array PERF_FUNCOES][PERF_HIST_SIZE], posição atual, flag de full.
Suporte adicional para exportação/importação textual do histórico de performance via download/upload de backup (endpoints /api/download_perf e /api/upload_perf).
Amostragem: 1 ponto a cada 5 segundos (PERF_SAMPLE_MS = 5000). Com 60 amostras, total = 300 segundos = 5 minutos de histórico.
Backup automático: Executado a cada 2 horas (padrão configurável via /api/config/set) ou sob demanda (/api/salvar).

8 Resultados
Os resultados indicam que o sistema atingiu os objetivos centrais de um CPS funcional: integração de hardware heterogêneo (OLED, LCD, DHT22, RTC, I2S, botões), firmware com monitoramento interno e interface web embarcada para operação e configuração. O dispositivo manteve operação contínua com sincronização de horário, gerenciamento de três alarmes, aquisição de temperatura/umidade local via DHT22 e consulta de clima externo por API. A camada de observabilidade permitiu diagnóstico operacional por logs e métricas, com visualização temporal em gráficos.
Métricas coletadas (7 séries em histórico circular de 5 minutos):
  [0] tempoLoopUs: Tempo total do ciclo principal (ms)
  [1] tempoPegarClimaUs: Tempo de requisição HTTP (ms)
  [2] tempoRtcNowUs: Tempo de leitura do RTC via I2C (ms)
  [3] tempoLeituraBotoesUs: Tempo de debounce dos botões (ms)
  [4] dhtTemperature: Temperatura medida pelo DHT22 (°C x10, inteiro)
  [5] tempoAtualizarDisplayUs: Tempo de redesenho do OLED (ms)
  [6] dhtHumidity: Umidade medida pelo DHT22 (% x10, inteiro)
Amostragem: 1 ponto a cada 5 segundos, totalizando 300 segundos (5 minutos) de histórico.
Indicadores adicionais: CPU estimada (%), heap livre/mínimo, stack disponível, uso de flash, PSRAM total/livre, número de tasks, status WiFi (CONECTADO/DESCONECTADO), status AP (ATIVO/INATIVO).


Em relação aos requisitos, os funcionais principais foram atendidos. Itens pendentes: [em desenvolvimento {multitarefa real em dual-core, interrupções de hardware com ISR, modo deep sleep com RTC_DATA_ATTR, e expansão de persistência para 24h com validação quantitativa}].




9 Conclusão
O projeto Relógio Inteligente ESP32 demonstrou a viabilidade de implementar um sistema ciberfísico completo em plataforma embarcada de baixo custo, com integração entre sensores, atuadores, conectividade e interface web. Os objetivos gerais e específicos foram majoritariamente alcançados, com destaque para configuração remota sem reflash, observabilidade integrada e persistência em flash. Itens não implementados: [em desenvolvimento {planejado evoluir com core pinning, fila/notificação inter-core, sleep modes e testes de watchdog/tolerância a falhas}].
Pontos implementados que podem melhorar {O que podia estar melhor}
- Endpoint de clima usa HTTP simples {trocar para HTTPS e timeout/retry exponencial para robustez e segurança}.
- Renderização da página web atualiza em intervalos fixos {aplicar cache local + atualização sob demanda para reduzir carga de CPU e rede}.
- Salvamento de backup em tempo fixo {usar política adaptativa por evento + consolidação em lote para reduzir escrita na flash}.

Apêndice C - Manual de Usuário
1) Alimentar o ESP32 (5V USB ou bateria).
2) Verificar no OLED o IP local (se WiFi conectado) ou AP de recuperação (se WiFi falhar). LCD 16x2 também exibe hora e IP/AP.
3) Acessar no navegador: http://<ip_local> (ex: http://192.168.0.20) ou http://192.168.4.1 (AP padrão).
4) Na aba "Principal": Ajustar hora do sistema, configurar 3 alarmes (hora, minuto, melodia, on/off), visualizar temperatura local (DHT22), umidade local, e clima da API.
5) Na aba "Monitoramento": Visualizar logs em tempo real (Logs), log serial (Serial), backup da flash (Flash), ou 7 gráficos de performance (Gráficos). Botões para forçar salvamento, baixar/restaurar backup de histórico.
6) Na aba "Sobre": Identificação do projeto (v3.1.0), ajustar intervalos de leitura DHT (ms), intervalo de clima (ms), intervalo de backup (ms), trocar SSID e senha do WiFi.
7) Usar botão 1 (GPIO4) para navegar menus no OLED; botão 2 (GPIO18) para confirmar. No display OLED: Relógio → Menu → Alarmes/Hora → Editar.
8) O sistema salva automaticamente configurações na flash. WiFi será reconectado ao reiniciar.
9) Para resetar: Renomeie /wifi_config.txt em SPIFFS ou faça format via Arduino IDE.
